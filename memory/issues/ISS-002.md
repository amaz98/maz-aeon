# ISS-002 — Recurring 08:00 UTC heartbeat dispatch slot skips

## Observation

`heartbeat` is the only enabled skill. It is scheduled 3× daily at 08:00 / 14:00 / 20:00 UTC via `aeon.yml`. The 08:00 UTC slot has been skipped 3 days in a row, and the broader recent window shows a >50% skip rate.

Recent slot dispatch pattern (2026-08-27 20:00 UTC → 2026-09-02 14:00 UTC, 18 slots):

| Slot | Dispatched? |
|------|-------------|
| 2026-08-27 20:00 | ❌ skipped |
| 2026-08-28 08:00 | ❌ skipped |
| 2026-08-28 14:00 | ✅ ran at 15:52 |
| 2026-08-28 20:00 | ❌ skipped |
| 2026-08-29 08:00 | ❌ skipped |
| 2026-08-29 14:00 | ❌ skipped |
| 2026-08-29 20:00 | ❌ skipped |
| 2026-08-30 08:00 | ❌ skipped |
| 2026-08-30 14:00 | ✅ ran at 15:03 |
| 2026-08-30 20:00 | ✅ ran at 21:33 |
| 2026-08-31 08:00 | ❌ skipped |
| 2026-08-31 14:00 | ✅ ran at 15:30 |
| 2026-08-31 20:00 | ✅ ran at 21:03 |
| 2026-09-01 08:00 | ❌ skipped |
| 2026-09-01 14:00 | ✅ ran at 15:08 |

| 2026-09-02 08:00 | ❌ skipped |
| 2026-09-02 14:00 | ✅ ran at 15:03 (this run) |

Skip rate: **10/18 = 56%**. Well above the 30% threshold ISS-001 set for re-opening.

The heartbeat workflow itself still always completes successfully once dispatched (`total_runs=262`, `total_successes=262`, `consecutive_failures=0` in `cron-state.json`) — the problem is again GitHub Actions failing to fire the cron on schedule, with a strong bias toward skipping the 08:00 UTC slot.

## Escalation trigger

ISS-001 was resolved on 2026-07-03 with an explicit rule: *"If skips resume with rate > 30%, re-open as a new issue and pursue the mitigations proposed above."* Current rate is 56% over 18 slots and the 08:00 skip has repeated on 3 consecutive days, so the condition is met.

## Suspected root cause

Same class as ISS-001 — GitHub-side best-effort scheduling on public-repo Actions crons — but with a much stronger 08:00 UTC bias this time. Possibilities:

1. Sustained platform-wide load around 08:00 UTC (peak global cron pileup).
2. Repo inactivity throttling — recent commits are mostly `chore(cron): heartbeat success` autocommits; substantive human commits are sparse.
3. Workflow file idiosyncrasy that gets deprioritized on morning slots specifically.

## Next steps (proposed)

Same mitigations proposed by ISS-001, but now worth actually implementing:

- Add a redundant cron entry at 08:05 / 14:05 / 20:05 UTC (or a `*/30` compensator that no-ops when the last run is fresh).
- Add an external ping (e.g. cron-job.org or an uptime service) that fires `workflow_dispatch` via the GitHub API at 08:00 UTC as a fallback for the most-skipped slot.
- Investigate whether a substantive weekly commit (docs update, README refresh) improves scheduling priority for public repos.
